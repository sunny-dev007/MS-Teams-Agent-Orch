Deployment Process

Your project deploys to Azure App Service via Azure DevOps Pipelines (not GitHub Actions). The git remote points to Azure DevOps:

origin  https://Az-FullStack@dev.azure.com/Az-FullStack/Project-NIT/_git/web.Whatsapp-AI-Agent

How Deployment Works (Step by Step)

1

Push code to Azure DevOps — git push origin main to the web.Whatsapp-AI-Agent repo

2

Pipeline triggers automatically — azure-pipelines.yml is configured to trigger on pushes to the main branch only

3

Build & Test stage — Installs Python 3.12, runs BaseSettings import guard, route mount guard, and all 89 pytest tests

4

Stage source package — rsync source files (excluding .git, .venv, .env, agent.db, workspaces, __pycache__) into a zip artifact

5

Deploy stage — Only runs when source branch is refs/heads/main AND build reason is not PullRequest

6

Oryx remote build — Uploads zip to Kudu async zipdeploy. App Service builds the Python virtualenv (antenv) on the server itself, avoiding GLIBC mismatch

7

Health check verification — Polls /health endpoint up to 80 times (15s apart = 20 minutes) until HTTP 200

Key detail: The pipeline uses the Azure service connection named "AI Copilot". If this service connection doesn't exist in your Azure DevOps project, the pipeline will fail at the Deploy stage.

Why Your Pipeline Didn't Run

There are several possible reasons:

1. No pipeline created in Azure DevOps

Having azure-pipelines.yml in the repo is not enough. You must also create a pipeline in Azure DevOps that references it:

Azure DevOps → Project Project-NIT → Pipelines → New Pipeline → Azure Repos Git → select web.Whatsapp-AI-Agent → Existing Azure Pipelines YAML file → select /azure-pipelines.yml

2. Pushed to wrong branch

The pipeline only triggers on the main branch. If you pushed to a feature branch (e.g., agent/xxx), only PR validation runs (tests only, no deploy). The Deploy stage condition is:

condition: and(
  succeeded('Build'),
  eq(variables['Build.SourceBranch'], 'refs/heads/main'),
  ne(variables['Build.Reason'], 'PullRequest')
)

3. Pushed to GitHub instead of Azure DevOps

There are no GitHub Actions workflows in this project (no .github/workflows/ directory). Pushing to GitHub won't trigger any pipeline. Your deploy remote must be Azure DevOps.

4. Service connection missing

The pipeline uses service connection "AI Copilot". Go to Project Settings → Service connections and verify it exists and is authorized for the pipeline.

Two-Layer Agent Architecture

Specialists (Graph Layer)

Thin wrappers in specialists/*.py. They implement the Specialist Protocol, call the agent function, and tag() the result with handled_by. They are LangGraph nodes.

Agents (Business Logic)

Pure async functions in agents/*.py. They take AgentState and return AgentState. No graph awareness — testable independently. They call services directly.

Plugin Agent Registry (New)

Leaf agents self-register via @register_agent decorator. Adding a new agent = one file with the decorator. The graph and planner discover agents automatically at startup via discover_agents().

LLM Codebase Context Prompt

Copy the prompt below and paste it into any LLM (GPT-4, Claude, Gemini) to give it complete understanding of this codebase. It covers architecture, business logic, all agents, services, and key patterns.

You are analyzing the "WhatsApp AI Agent" codebase — a multi-agent LLM-powered automation platform where a user interacts via WhatsApp to orchestrate automated workflows including email management, calendar scheduling, code development, review, and deployment. ## Architecture - **Runtime**: Python 3.12 + FastAPI + Uvicorn - **AI Orchestration**: LangGraph StateGraph (38 nodes, 7+ conditional edges, AsyncSqliteSaver checkpointing) - **LLM**: Azure OpenAI (GPT-4o-mini for routing, GPT-4.1 for codegen/review) via langchain-openai - **Messaging**: WhatsApp Cloud API (Meta Graph API v21) - **Email**: Gmail API (OAuth2 — gmail.readonly + gmail.send scopes) - **Calendar**: Google Calendar API (calendar.events scope, Google Meet links) - **Source Control**: GitHub REST API + Azure DevOps REST API v7.1 - **Git**: GitPython with HTTP API fallback (GitHub Git Data API / AzDO Pushes API) for environments without git binary - **Database**: SQLite + aiosqlite + SQLAlchemy 2.0 (async), persisted at /home/site/data/agent.db on Azure - **Hosting**: Azure App Service (B1 Linux), Oryx remote build, Azure DevOps CI/CD ## Two-Layer Agent Architecture 1. **Specialists** (src/agent/specialists/*.py): Thin LangGraph node wrappers implementing the Specialist Protocol. They call the agent function and tag() the result with handled_by. 2. **Agents** (src/agent/agents/*.py): Pure async functions (AgentState) → AgentState. No graph awareness — testable independently. They call services directly. ## Plugin Agent Registry Leaf agents self-register via @register_agent decorator in specialists/*.py. The graph and planner discover agents automatically at startup via discover_agents(). - 6 registered leaf agents: email_agent, send_email_agent, calendar_agent, repo_wizard, task_status_agent, general_agent - The coding pipeline (architect → plan approval → developer → reviewer → PR → deploy) remains a static subgraph ## Core Flow: WhatsApp Message → Response 1. POST /webhooks/whatsapp → HMAC-SHA256 verify → phone allowlist → gate routing 2. FastAPI BackgroundTasks dispatches to handle_whatsapp_message() 3. Fast-path: greetings/help → direct WhatsApp reply (skip graph entirely) 4. LangGraph StateGraph executes: planner → [specialist agent] → notifier → evaluator 5. For coding tasks: planner → architect (plan) → [plan approval gate] → developer (codegen) → reviewer (max 3 loops) → PR publish → [PR review mode gate] → [deploy approval gate] → deployer (merge + CI) → CI watch ## Multi-Gate Workflow (Human-in-the-Loop) The graph pauses at gates where the user must respond via WhatsApp: - GATE_PLAN: "PROCEED {task_id}" or "REJECT {task_id}" after architect generates implementation plan - GATE_PR_MODE: "1" (AI review) or "2" (manual review) after PR is created - GATE_MANUAL_PR: "PR READY {task_id}" after manual PR review - GATE_DEPLOY: "APPROVE {task_id}" or "REJECT {task_id}" before merging and deploying - GATE_CI_FIX: "FIX TESTS {task_id}" or "SKIP FIX" when CI fails Gate state is persisted in both SQLite (ConversationSession) and durable gate files (/home/site/data/workflow_gates/) to survive Azure App Service container restarts. ## Key Services - **services/llm.py**: Multi-deployment LLM with role-based routing (deployment_chain), per-deployment retries, automatic fallback across deployments on rate limits - **services/git_ops.py**: Git operations with 3-tier fallback: system git → GitHub zipball/AzDO zip → HTTP API push (blob+tree+commit) - **services/ci_gate.py**: Provider-isolated CI busy checks and in-process deploy locks — prevents concurrent deploys - **services/ci_watch.py**: Durable CI pipeline monitoring with DB persistence, background polling, WhatsApp notifications on completion, automatic test fixer offers on failure - **services/code_guards.py**: Safety layer that sanitizes LLM-generated file changes — prevents breaking config.py, removing FastAPI routers, writing to wrong paths ## AgentState TypedDict The full state dictionary flowing through the LangGraph with fields for: task_id, status, source, intent, user_message, email context, repo context, session/multi-turn state, meeting details, developer output (file_changes, workspace_path), multi-gate workflow (implementation_plan, pr_review_mode, pr_number), review output (review_result, review_iteration), human approval, deployment output (commit_sha, pr_url, pipeline_status), CI test-fixer, evaluation, and communication (whatsapp_phone, notification_text, messages, error). ## Project Structure src/agent/ ├── main.py # FastAPI app, lifespan (discover_agents → init_db → deferred startup) ├── config.py # Pydantic Settings from .env (Azure OpenAI, WhatsApp, Gmail, GitHub, AzDO) ├── registry.py # @register_agent decorator + plugin registry ├── discovery.py # Auto-discovery via pkgutil.walk_packages ├── api/ # FastAPI routers (whatsapp, gmail, health, tasks, portal) ├── agents/ # Business logic (graph, developer, reviewer, architect, deployment, notification, evaluator, gmail_agent, meeting, pr_publisher, pr_reviewer, test_fixer) ├── planner/ # Intent classification (regex fast-path → LLM fallback) ├── specialists/ # Thin graph-wired wrappers with @register_agent decorators ├── services/ # External API clients (whatsapp, gmail, github, azure_devops, llm, git_ops, ci_gate, ci_watch, calendar, code_guards, deploy_notify) ├── core/ # Infrastructure (security, session, background, oauth, gate_store, persona, logging) ├── workflow/ # Gate constants, session persistence, resume formatting ├── models/ # SQLAlchemy ORM (Task, ConversationSession, PendingCiWatch) ├── prompts/ # LLM prompt templates (.txt files) └── web/ # Portal HTML ## Key Design Patterns 1. **State Spread**: Every agent returns {**state, "status": "new", "notification_text": "..."} 2. **Fast-Path**: Simple greetings skip the entire LangGraph (direct WhatsApp reply) 3. **Session-Aware Multi-Turn**: ConversationSession tracks awaiting state for wizards and gates 4. **Provider Dispatch**: Routes to GitHub or Azure DevOps based on repo_url 5. **Durable Gates**: Gate state persisted to both SQLite and filesystem to survive App Service restarts 6. **Code Guards**: LLM output sanitized before disk write to prevent self-destructive changes 7. **CI Watch**: Background poller monitors pipeline, offers test fixer on failure, sends WhatsApp on completion When answering questions about this codebase, use these file paths and function names as references. The codebase is at src/agent/ with tests at tests/.
